1. **[P2] A recording start can finish after background suspension without being stopped.** Primary location: `/tmp/english-research-docs/src/app/application.ts:200`; suspension guard at `/tmp/english-research-docs/src/app/application.ts:278`. The controller sets `recording=true` only after awaiting `platform.startRecording()`. If suspension occurs while that await is pending, `suspend()` sees `recording=false`, skips stopping, and returns. The original operation can subsequently resolve and set recording active while the page is already hidden. There is no cancellation generation or pending-start state checked before accepting the result.

   Reproduction: initialize a speaking session, use a deferred promise for `Platform.startRecording`, call `const starting = app.action('record-start')`, await `app.suspend()`, resolve the deferred start, then await `starting`. Observed: `stopRecording` calls remain zero and `app.render().question.recording === true`. The isolated probe asserts these values and exits 0.

   Native connection: `/tmp/english-research-docs/src/native/app.ts:86` awaits privacy authorization, microphone authorization and recorder `onStart` before resolving. `/tmp/english-research-docs/miniprogram/components/app-shell/index.js:15` suspends and clears the ticker on hide; `/tmp/english-research-docs/miniprogram/app.js:2` also suspends on app hide. Therefore the asynchronous start window exists in the actual adapter; duplicate hide callbacks both see recording false and do not fix the race. This violates architecture's promise that backgrounding stops/saves active recording. Exact duration or operating-system microphone behavior after hide was not measured: the proof is a deterministic controller/platform-double interleaving, not a real-device recording claim. Fix direction: track pending start and suspension/cancellation, stop/save a late start before accepting it, and test hide while authorization/start is pending.
